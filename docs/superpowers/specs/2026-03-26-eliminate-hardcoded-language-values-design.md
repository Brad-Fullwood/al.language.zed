# Eliminate Hardcoded AL Language Values — Design Spec

**Date:** 2026-03-26
**Status:** Draft
**Problem:** AL language data (keywords, built-in functions, types, object types, implicit variables) is hardcoded as const arrays and match blocks in 20+ locations across 6 Rust crates. These lists are incomplete, inconsistent with each other, and will silently become stale when Microsoft updates AL.

## Principle

**tree-sitter-al is the single authority on what AL looks like.** The al- Rust crates never touch Microsoft DLLs for base language data — they consume what tree-sitter-al generated. al-semantic enriches with version-specific info from a live .NET bridge but never provides base data.

## Data Flow

```
tree-sitter-al/generator/tools/al-extract/
    reads: MS .NET DLLs (CodeAnalysis, EditorServices) + TextMate grammar
    generates:
        tree-sitter-al/data/*.json       (language data files)
        tree-sitter-al/src/*             (grammar C source)
        tree-sitter-al/queries/*         (highlights, indents, etc.)

al-syntax, al-symbols, al-core
    reads: tree-sitter-al/data/*.json via include_str! at compile time
    never: touches Microsoft DLLs for base language data

al-semantic
    enriches: version-specific details on top of complete base data
    never: fills gaps in base data
```

## Generated Data Files

All files live in `tree-sitter-al/data/` and are generated by al-extract.

### `keywords.json`

All AL keyword categories with their tree-sitter node kind names.

```json
{
  "control": [
    {"keyword": "begin", "node_kind": "kw_begin"},
    {"keyword": "end", "node_kind": "kw_end"},
    {"keyword": "if", "node_kind": "kw_if"},
    ...
  ],
  "object": [
    {"keyword": "table", "node_kind": "kw_table"},
    {"keyword": "page", "node_kind": "kw_page"},
    ...
  ],
  "type": [
    {"keyword": "Integer", "node_kind": "kw_integer"},
    {"keyword": "Decimal", "node_kind": "kw_decimal"},
    ...
  ],
  "operator": [
    {"keyword": "and", "node_kind": "kw_and"},
    {"keyword": "or", "node_kind": "kw_or"},
    ...
  ],
  "metadata": [...],
  "property": [...]
}
```

**Source:** TextMate grammar (already extracted by al-gen) + grammar.js node kinds.

**Consumers:** al-syntax (semantic token classification, completions keyword lists), al-core (completion candidates, code action keyword checks).

### `builtin_functions.json`

Global AL built-in functions with full signatures.

```json
[
  {
    "name": "Message",
    "signature": "Message(String: Text [, Value: Any, ...])",
    "parameters": [
      {"name": "String", "type": "Text", "required": true, "description": "The message format string."},
      {"name": "Value", "type": "Any", "required": false, "variadic": true, "description": "Substitution values."}
    ],
    "return_type": null,
    "description": "Displays a message to the user.",
    "category": "dialog"
  },
  ...
]
```

**Source:** .NET `Microsoft.Dynamics.Nav.CodeAnalysis.dll` — reflect over global function definitions.

**Consumers:** al-syntax (semantic token classification — function names), al-core (completions, hover documentation, signature help).

### `object_types.json`

AL object type metadata.

```json
[
  {
    "keyword": "table",
    "display_name": "Table",
    "node_kind": "kw_table",
    "extensions": ["tableextension"],
    "lsp_symbol_kind": "Class"
  },
  {
    "keyword": "page",
    "display_name": "Page",
    "node_kind": "kw_page",
    "extensions": ["pageextension", "pagecustomization"],
    "lsp_symbol_kind": "Class"
  },
  ...
]
```

**Source:** TextMate grammar + grammar.js.

**Consumers:** al-syntax (document symbols, navigation), al-symbols (ObjectKind parsing, symbol index), al-core (completions, code actions).

### `implicit_variables.json`

Implicit trigger-context variables. Replaces current `builtin_variables.json`.

```json
[
  {"name": "Rec", "type": "Record", "context": ["table_trigger", "page_trigger"], "description": "The current record."},
  {"name": "xRec", "type": "Record", "context": ["table_trigger", "page_trigger"], "description": "The previous version of the record."},
  {"name": "CurrPage", "type": "Page", "context": ["page_trigger"], "description": "The current page object."},
  {"name": "CurrReport", "type": "Report", "context": ["report_trigger"], "description": "The current report object."},
  {"name": "CurrFieldNo", "type": "Integer", "context": ["table_trigger"], "description": "The field number that triggered the event."},
  {"name": "RequestOptionsPage", "type": "Page", "context": ["report_trigger"], "description": "The request options page for the report."}
]
```

**Source:** .NET DLLs.

**Consumers:** al-syntax (semantic token classification), al-core (completions, type resolution).

### `page_controls.json`

Structural page/report layout keywords.

```json
["area", "group", "repeater", "field", "part", "action", "separator", "cuegroup", "grid", "fixed", "usercontrol", "label", "dataitem", "column", "filter", "addfirst", "addlast", "addafter", "addbefore", "modify", "moveafter", "movebefore", "actionref"]
```

**Source:** TextMate grammar or grammar.js page-related rules.

**Consumers:** al-syntax (document symbol nesting for page objects).

### `runtime_enums.json`

Enum types that exist at runtime but are not published in any .app package.

```json
[
  {"name": "SecurityFilter", "values": ["Disallowed", "Validated", "Filtered", "Ignored"]},
  {"name": "TestPermissions", "values": ["Disabled", "Restrictive", "NonRestrictive", "InherentPermissions"]},
  ...
]
```

**Source:** .NET DLLs — reflect over runtime enum types.

**Consumers:** al-symbols (symbol index, runtime enum loading).

### `token_classification.json`

Maps tree-sitter node kinds to semantic token types. Derived from the keyword categories above, but expressed as the direct node-kind → token-type mapping that tokens.rs needs.

```json
{
  "keyword_control": ["kw_begin", "kw_end", "kw_if", "kw_then", "kw_else", "kw_for", "kw_while", "kw_repeat", "kw_until", "kw_case", "kw_exit", "kw_break", "kw_do", "kw_foreach", "kw_in", "kw_to", "kw_downto", "kw_with", "kw_asserterror"],
  "keyword_object": ["kw_table", "kw_page", "kw_codeunit", "kw_report", "kw_query", "kw_xmlport", "kw_enum", "kw_interface", "kw_permissionset", "kw_profile", "kw_controladdin", "kw_entitlement", "kw_dotnet"],
  "keyword_object_extension": ["kw_tableextension", "kw_pageextension", "kw_reportextension", "kw_enumextension", "kw_permissionsetextension", "kw_pagecustomization", "kw_profileextension"],
  "builtin_type": ["kw_integer", "kw_decimal", "kw_text", "kw_code", "kw_boolean", "kw_date", "kw_time", "kw_datetime", "..."],
  "builtin_function": ["Message", "Error", "Confirm", "Format", "..."]
}
```

**Source:** Derived from keywords.json categories + grammar node kind naming convention.

**Consumers:** al-syntax (semantic token classification in `classify_node`).

## Loading in Rust Crates

### al-syntax: Primary loader

New module `al-syntax/src/language_data.rs`:

```rust
use std::sync::LazyLock;
use serde::Deserialize;

// Typed structs for each data file
#[derive(Deserialize)]
pub struct KeywordEntry { pub keyword: String, pub node_kind: String }

#[derive(Deserialize)]
pub struct Keywords {
    pub control: Vec<KeywordEntry>,
    pub object: Vec<KeywordEntry>,
    pub r#type: Vec<KeywordEntry>,
    pub operator: Vec<KeywordEntry>,
    pub metadata: Vec<KeywordEntry>,
    pub property: Vec<KeywordEntry>,
}

#[derive(Deserialize)]
pub struct BuiltinFunction {
    pub name: String,
    pub signature: String,
    pub parameters: Vec<Parameter>,
    pub return_type: Option<String>,
    pub description: String,
    pub category: String,
}
// ... etc for each data type

// LazyLock loaders
static KEYWORDS: LazyLock<Keywords> = LazyLock::new(|| {
    serde_json::from_str(include_str!("../../../tree-sitter-al/data/keywords.json"))
        .expect("keywords.json must be valid")
});

pub fn keywords() -> &'static Keywords { &KEYWORDS }
pub fn builtin_functions() -> &'static [BuiltinFunction] { &BUILTIN_FUNCTIONS }
pub fn object_types() -> &'static [ObjectType] { &OBJECT_TYPES }
pub fn implicit_variables() -> &'static [ImplicitVariable] { &IMPLICIT_VARIABLES }
pub fn page_controls() -> &'static [String] { &PAGE_CONTROLS }
pub fn token_classification() -> &'static TokenClassification { &TOKEN_CLASSIFICATION }
```

### al-symbols: Loads object_types.json directly

al-symbols cannot depend on al-syntax (dependency rule). It loads `object_types.json` directly with its own minimal deserializer. Same data file, same source of truth — just a separate loader because of the dependency constraint.

### al-core: Uses al-syntax's API

al-core depends on al-syntax, so it accesses everything through `al_syntax::language_data::*`.

## al-extract Changes

Extend `tree-sitter-al/generator/tools/al-extract/` to:

1. **Read .NET CodeAnalysis DLL** — reflect over global built-in function definitions to extract names, parameter lists, return types, and XML doc comments
2. **Read .NET runtime enums** — extract enum types not published in .app packages (SecurityFilter, TestPermissions, etc.)
3. **Read implicit variable definitions** — extract trigger-context variables with their types and contexts
4. **Output all data files** to `tree-sitter-al/data/`
5. **Derive token_classification.json** from keyword categories + grammar node naming convention

The TextMate grammar extraction for keywords, types, and object types already works — al-extract just needs to output the new JSON format alongside the existing grammar generation.

## What Stays Hardcoded (Not Language Data)

These are NOT AL language data and remain as code:

- `SINGLE_STMT_OPENERS` in formatting.rs — formatter control flow behavior
- `SECRET_PATTERNS` in lint.rs — security heuristic pattern matching
- `DIAGNOSTICS_DEBOUNCE` in server.rs — server tuning constant
- `SUPPRESSED_KINDS` in completions.rs — tree-sitter node kind filtering (comment/string)
- Lint rule metadata (`RULES` in lint.rs) — our rules, not Microsoft's language

## Enrichment via al-semantic

al-semantic enriches the base data at runtime:
- Functions added in newer BC versions not yet in the extraction DLLs
- Deprecation notices for functions/types
- Version-specific parameter changes
- Project-specific type information from the workspace's BC version

This is additive. The base data from tree-sitter-al is always complete and functional without al-semantic.

## Testing

- Each data file gets a validation test: parse, check non-empty, check required fields
- Existing tests continue to pass — behavior is identical, source changes from hardcoded to data-driven
- Integration test: modify a data file, verify the change propagates to completions/hover/etc.
