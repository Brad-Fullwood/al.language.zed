# Releasing the AL extension

This repo ships two things a new user needs:

1. The **WASM extension** (`zed-al`), which Zed loads.
2. The **`al-lsp` binary** (built from `al-core`), which the extension downloads
   from a GitHub Release the first time it runs (when `al-lsp` is not already on
   `$PATH` and the user has not set `lsp.al-lsp.binary.path`).

If no Release exists, step 4 of the extension's resolution chain
(`find_or_download_binary` in `src/lib.rs`) fails and the language server never
spawns for a fresh user. **Cutting a Release is therefore a hard requirement
for the extension to work out of the box.**

When that step fails — whether because no Release exists yet, the network blocks
GitHub, or no asset matches the user's platform — the extension now surfaces an
actionable error (the releases URL, a copy-paste `lsp.al-lsp.binary.path`
settings snippet, and the `cargo install` / PATH fallback) instead of a raw
"no releases found". So a user can recover manually even before the first tag is
pushed. Cutting a Release is still required for the zero-config experience; the
actionable error is the safety net. The `release_lookup_failure_is_actionable`
and `asset_not_found_is_actionable` tests in `src/repo_consistency_test.rs` pin
this guidance so a refactor cannot silently drop it.

## The release gate is a pushed tag

`.github/workflows/release.yml` runs **only** on a pushed tag matching `v*`. No
tag → no Release → no downloadable `al-lsp`. (This was the original silent
deployment gap: the pipeline was ready but no tag had ever been pushed.)

## Cutting a release

```sh
# 1. Make sure dev is green and the version is bumped consistently.
./scripts/bump-version.sh 0.2.0        # updates Cargo.toml(s) + extension.toml
./scripts/check-repo-consistency.sh    # GITHUB_REPO == extension.toml == git remote
cargo test --workspace --exclude zed-al
cargo test -p zed-al                   # host unit tests (repo-slug guard etc.)

git commit -am "chore: release v0.2.0"
git push origin dev

# 2. Tag and push the tag — THIS triggers release.yml.
git tag v0.2.0
git push origin v0.2.0
```

## What the pipeline produces

`release.yml` builds `al-lsp` for **five** targets and uploads one archive per
target to the GitHub Release, plus a `checksums.txt`. The asset names MUST match
exactly what `src/lib.rs` requests in `find_or_download_binary`:

| Platform (`current_platform()`) | Release asset name        | Contains                                  |
|---------------------------------|---------------------------|-------------------------------------------|
| Linux x86_64                    | `al-linux-x86_64.tar.gz`  | `al-lsp`, `al-explorer`, `bridge/`        |
| Linux aarch64                   | `al-linux-aarch64.tar.gz` | `al-lsp`, `al-explorer`, `bridge/`        |
| macOS x86_64                    | `al-macos-x86_64.tar.gz`  | `al-lsp`, `al-explorer`, `bridge/`        |
| macOS aarch64                   | `al-macos-aarch64.tar.gz` | `al-lsp`, `al-explorer`, `bridge/`        |
| Windows x86_64                  | `al-windows-x86_64.zip`   | `al-lsp.exe`, `bridge/`                   |

The binaries sit at the **archive root** (no wrapping directory). Zed's
`download_file` (`GzipTar` on Unix, `Zip` on Windows) extracts them into the
extension work dir, and the extension runs `<work-dir>/al-lsp[.exe]` — exactly
the `binary_path` `src/lib.rs` constructs.

**Semantic bridge.** al-lsp is built with `--features semantic` so it contains
the real in-process .NET CLR host (not the no-op stub). `build.rs` produces
`AlBridge.dll` (platform-agnostic .NET IL) via `dotnet build`; the pipeline
bundles it under `bridge/` next to the binary, where the runtime finds it
(`semantic::host::find_bridge_dll` Strategy 2: `<exe-dir>/bridge/`). The release
jobs install the .NET 8 SDK for this. For the cross-compiled aarch64 build
(`dotnet` is absent inside the `cross` container) the bridge is built on the
host first and passed in via `AL_BRIDGE_PREBUILT`, which `build.rs` copies
instead of invoking `dotnet`. The bridge's `runtimeconfig.json` sets
`RollForward=Major`, so it runs on any .NET 8+ runtime the user has installed.

`checksums.txt` (SHA-256 of every archive, generated by the `create-release`
job) lets manual installers verify integrity.

> **Keep code and pipeline aligned.** If you change the matrix `artifact_name`
> values or extensions in `release.yml`, you MUST update the asset-name logic in
> `src/lib.rs` (and vice-versa). The `release_asset_names_match_workflow` test in
> `src/repo_consistency_test.rs` fails the build if they drift.

## Windows

Windows **is** published, but only the `al-lsp` binary. `al-explorer`'s daemon
IPC client uses an `AF_UNIX` socket (F-020/F-021) and does not compile on
Windows; the daemon transport in `al_core::server::daemon` is therefore behind
`#[cfg(unix)]` with a `#[cfg(not(unix))]` stub. `al-lsp` itself is portable — its
LSP (`--stdio`) and DAP (`--dap`) modes use platform-neutral stdio over
`tower-lsp` — so Zed spawns it normally on Windows. Daemon mode (used only by the
`al-explorer` TUI/CLI) is not available on Windows. See `ecosystem-roadmap.md`
item 8 / strategic bet 3b.

The Windows matrix entry is flagged `windows: true`, which (a) skips the
`al-explorer` build and (b) packages a `.zip` instead of a `.tar.gz`.

## Verifying a release worked

After the workflow completes:

```sh
gh release list
gh release view v0.2.0   # confirm the five al-* archives + checksums.txt are attached
```

Then install the dev extension in Zed on a machine without `al-lsp` on `$PATH`
and confirm the language server downloads and starts (test on Windows too).
