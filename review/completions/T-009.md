# T-009: Fix al-semantic Mutex poisoning — don't recover corrupt CLR state

## Status: COMPLETED

## Task
Replace `e.into_inner()` with error return when the Mutex is poisoned in the al-semantic CLR bridge.

## Changes Made
- **File:** `crates/al-semantic/src/lib.rs`
- **Added:** New `SemanticError::Poisoned` variant:
  ```rust
  #[error("Bridge Mutex is poisoned — CLR state may be corrupt after a panic")]
  Poisoned,
  ```
- **Changed (line ~225):** Replaced:
  ```rust
  let guard = host.lock().unwrap_or_else(|e| {
      tracing::warn!("SemanticBridge Mutex was poisoned — recovering inner value");
      e.into_inner()
  });
  ```
  With:
  ```rust
  let guard = host.lock().map_err(|_| SemanticError::Poisoned)?;
  ```

## Validation
- Compilation: `cargo check -p al-semantic` — PASS
- This is distinct from the tower-lsp poisoned lock pattern (which uses `into_inner()` safely) — the CLR bridge Mutex protects FFI state that may be corrupt after a panic

## Justification
The CLAUDE.md documents `unwrap_or_else(|e| e.into_inner())` for tower-lsp locks, where the protected state is Rust data that can tolerate recovery. The al-semantic Mutex protects a .NET CLR bridge — if a panic occurs during FFI, the CLR runtime state may be corrupt. Continuing to use a corrupt CLR bridge could cause undefined behavior, data corruption, or crashes. Returning an error allows the caller to handle the situation gracefully.
