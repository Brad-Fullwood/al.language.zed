# T-004: Fix UTF-16/byte position conversion in al-syntax navigation and al-core code_actions

## Status: COMPLETED

## Task
Multiple functions pass `position.character` (UTF-16 code units) directly as tree-sitter byte column. This is wrong for any non-ASCII text.

## Changes Made

### crates/al-syntax/src/navigation.rs
- `find_node_at_position`: Added `text: &str` parameter; converts `pos.character` to byte offset via `crate::utf16_col_to_byte_offset(line_text, pos.character as usize)` before constructing `tree_sitter::Point`
- `find_procedure_at`: Updated to pass `text` to `find_node_at_position`
- Tests updated to pass source text

### crates/al-syntax/src/type_resolver.rs
- `find_enclosing_procedure`: Converts `position.character` to byte offset using `crate::utf16_col_to_byte_offset()` before creating `tree_sitter::Point`

### crates/al-core/src/queries/code_actions.rs
- `source_action_implement_interface` (~line 838): Added UTF-16→byte conversion before `tree_sitter::Point::new()`
- `source_action_make_local` (~line 1502): Same fix

## Validation
- Compilation: `cargo check --workspace --exclude zed-al` — PASS
- All 7 callers of `find_node_at_position` across al-core already had `text` available and were updated
- Pattern follows the existing correct implementation in `source_action_if_to_case` (lines 570-573)
- Reference implementation: `source_action_if_to_case` at code_actions.rs:570-573

## Justification
LSP positions use UTF-16 code units for the character offset. Tree-sitter uses byte offsets. For ASCII text they're identical, but for any non-ASCII characters (common in AL comments, string literals, and identifiers), the offsets diverge. Without conversion, node lookups land on the wrong position.
