# T-008: Fix zed-al WASM relative path resolution for binary cache

## Status: FALSE POSITIVE — NO CHANGE NEEDED

## Task
`fs::metadata(&binary_path)` supposedly uses relative paths that resolve against WASM CWD, not extension work dir.

## Investigation
- **File:** `src/lib.rs` lines 60-64 and 118-150
- The `binary_path` is relative (e.g., `al-lsp-1.2.3/al-lsp`)
- In Zed's WASM extension host, the preopened directory IS the extension's work directory
- `fs::metadata()` resolves relative paths against this preopened directory
- `zed::download_file()` saves files to paths relative to the same work directory
- Both APIs use the same base — relative paths are consistent

## Validation
- This is how Zed extensions are designed to work — the WASM sandbox filesystem is rooted at the extension work directory
- The same pattern is used in other Zed extensions (e.g., the official Rust extension)
- No compilation or runtime evidence of path resolution failure

## Justification
No change needed. The review finding assumed that WASM CWD and extension work dir are different, but in Zed's extension host they are the same thing. The preopened directory that WASI `fs` operations resolve against is the extension work directory.
