# Round 6 security review: surfaces the earlier rounds did not reach

Reviewer brief: the sixth security round. Look at the surfaces that rounds 2 to 5 did not cover, or that changed since: the links inside trust inputs after the SEC5 fixes, the legacy proxy's key check, the persisted dependency source index, the local test runtime, daemon methods added since round 4, the Claude Code plugin scripts, and the text of refusal and error messages. Review only, no code changes. Round 11 (`campaign/r11-review`) re-checks the round 5 fixes, so this round does not repeat that.

Scope: the tree at `14381c32` on `campaign/2026-09-21`, with weight on `crates/al-project`, `crates/al-lsp/src/server/dap_mode`, `crates/al-workspace`, `crates/al-analysis`, `crates/al-runtime`, `crates/al-test`, `crates/al-lsp/src/server/daemon` and `plugin/scripts`.

Branch reviewed: `campaign/r6-security` at `14381c32`.

Threat model: a developer opens a hostile repository, `.app` package or test file in the editor, or runs `al-explorer` on it, before trusting the project. A second attacker is a local process of another user on a shared machine. The assets are the user's credentials, the trust digest and the daemon.

Tools: reading the source, scratch tests run one crate at a time with `cargo test`, the release `al-explorer` on copies of the test project under `/tmp`, and small shell probes of the plugin scripts. Scratch tests are not committed. They are saved as `.campaign/r6-scratch-tests.patch` in the main checkout.

## Coverage

- [x] 1. Links in the trust inputs after SEC5 (`trust.rs`, `analyzers.rs`): a `.netpackages`, `packages` or probing path directory that links outside the project, and whether `record` and `load` resolve links the same way: SEC6-1, SEC6-2. Checked without a finding: the record (`find_in_project`, `with_project_contents`) and the loader (`discover`) walk the same roots with the same `find_best_below` and hand on the same canonical path, so for a target inside the project they agree. alc receives that canonical path, so a link swapped after `resolve` redirects nothing unless a directory on the canonical path is itself replaced, which inside the project needs a `git pull` during the build (the window SEC5 item 1 set aside). A link to a directory another user owns has no such limit: that user can replace the file between the hash and the load, which SEC6-1 notes.
- [x] 2. The legacy proxy's key check: `eq_ignore_ascii_case` and a key such as `ſerver` (U+017F), against the host's JSON binder: no finding. A copy of Microsoft's AL extension 18.0.2732683 on this machine ships EditorServices.Host (net10.0), so the host was decompiled rather than guessed at. The host reads the DAP envelope with `StringComparison.Ordinal` and binds `arguments` with a plain `JToken.ToObject<InitializeDebugAdapterRequest>()` (`RequestHandlerBase`), so Newtonsoft's default rule applies: the exact name, then `OrdinalIgnoreCase`. A probe that loads the extension's own `Newtonsoft.Json.dll` and `EditorServices.Protocol.dll` on .NET 10.0.12 binds `{"environmentType":"Sandbox","ſerver":…}` with `Server` null, and a sweep of every BMP character against `a` to `z` finds no pair that `OrdinalIgnoreCase` treats as equal, with ICU and with `DOTNET_SYSTEM_GLOBALIZATION_INVARIANT=1`. `ToUpperInvariant` does map U+017F to `S`, but the binder does not use it. So the set of spellings the host can bind to a target key is the ASCII case variants, which the proxy refuses. A scratch test (`r6_scratch_proxy_long_s_and_command_case` in `dap_mode`) shows the proxy forwards `ſerver` when the scenario is online and refuses it for `OnPrem` (no usable server), and in both cases the host sees no server. The same test shows the proxy judges only a `command` of exactly `launch` or `attach`, while the host's `RequestRegistry` looks handlers up with `StringComparer.OrdinalIgnoreCase`, so `Launch` would reach the launch handler unjudged. No repository can choose that string: the Zed extension maps `request` to Zed's two value enum (`src/dap.rs` `dap_request_kind`) and Zed writes the command, and nothing else starts `--dap-legacy`. Matching the command without case would cost nothing. The host also reads `entraIdAuthentication` (sign-in `endpoint`, `clientId`, `redirectUri`, `scope`), `accessToken`, `noAuth` and `environment` from the scenario (`DebugAdapterStartRequestHandler` builds its connection with `request.CreateConnectionOptions`). `environment` only picks among Microsoft host suffixes, and none of these keys changes the host the token is sent to, but `entraIdAuthentication.endpoint` becomes the MSAL authority. Whether MSAL's authority validation refuses an unknown host there, so that a repository cannot send the sign-in to its own page, was not checked [UNVERIFIED]. Windows with `System.Globalization.UseNls` was not checked either [UNVERIFIED].
- [x] 3. The persisted dependency source index: where the store lives, its permissions, what a crafted summary file does when loaded, key collisions between packages, two daemons writing one entry: no finding. The store is `<user data dir>/al-lsp/source-index`, created 0700 with entries 0600 through a `create_new` temporary file and a rename (`source_cache.rs`). Before any read, the directory and the entry must not be links, must belong to this uid and must not be writable by group or other, so only the user can plant or replace an entry, and a group writable parent does not help another user: a directory they put in its place is theirs and is refused. An entry over 256 MiB is refused before it is read, the body is plain serde data with no paths the loader acts on, and `load` compares the whole header key (schema, grammar and builder fingerprints, the SHA-256 and length of the `.app` bytes, app id, name, version) with the key of the package it is asked for. A summary holds only each file's archive path, and `dependency_virtual_path` builds the in-memory path from the loading project's own package path with `..` and root components dropped, so an entry written by one project carries nothing of that project into another. A hostile `.app` controls the readable part of its entry name (sanitised to `[A-Za-z0-9 ._-]`, 120 bytes) but the rest is an FNV-1a hash over the fingerprints and the SHA-256 of its own bytes. Colliding with another package's name would take a 64-bit second preimage through SHA-256, and even then the header comparison turns it into a miss and a rewrite, with no summary served for the wrong bytes. A manifest name containing `.tmp.` makes the entry look like a temporary file, so garbage collection deletes that package's own entry after a minute, which costs only a rebuild of that package. Two daemons write under different temporary names (pid and a sequence) and rename into place, the bytes are the same for the same key, and a collection in one daemon that deletes an entry another just wrote causes a miss. The 6280a560 check (key taken again after the build) holds, and flipping a package's bytes and back during one build needs a writer in the project folder. Extraction limits (32 MiB per file, 1 GiB per package) are round 2's decompression bomb coverage. The navigation cache `~/.cache/al-lsp/symbols/<package>/` (`virtual_file.rs`) was read for the same questions: file names always end in `-<24 hex>.al`, so no `.dll` can be produced there for a SEC6-1 link to pick up, and a package named `..` puts its `.al` file one level up, still inside `~/.cache/al-lsp`.
- [ ] 4. The local test runtime as a surface for hostile AL: builtins that reach the host, endless loops and recursion, self referencing lists, dictionaries and text builders.
- [ ] 5. Daemon methods added or changed since round 4: capabilities declared and used, and whether tests drive them.

## Findings

### [SEC6-1] a `.netpackages` or `packages` link to a directory outside the project loads an analyzer the trust record does not list
- where: crates/al-project/src/analyzers.rs:207 (`resolve` returns any file outside the project at once, so `lists_project_copy` only ever judges files inside it), :411 (`find_best_below` reads the search root with `std::fs::metadata`, which follows a link, while :462 skips links below the root), :295 (in a trusted project `.netpackages` and `packages` are searched before the NuGet cache), against crates/al-project/src/trust.rs:505-506 (`linked_package_folders` records where `.alpackages` and the package cache folders resolve, and not `.netpackages` or `packages`)
- severity: medium
- scenario: the SEC5-8 shape with a link in place of a file. A developer names `"al.codeAnalyzers": ["BusinessCentral.LinterCop"]` in the `lsp.al-lsp.settings` of their Zed user settings and has LinterCop in the NuGet cache. They trust a repository whose only privileged value is an on-premises launch server. A later commit adds `.netpackages` as a link to `/tmp/bc-tools`, a directory another user of the same machine created and fills. The record does not change, so the state stays `Trusted`. `CustomAnalyzerSearch` searches `.netpackages` before the NuGet cache, the walk follows the link at its root and finds `/tmp/bc-tools/x/BusinessCentral.LinterCop.dll`, and `resolve` returns it because the canonical path is outside the project. The SEC5-8 fix, which refuses a copy the record does not list, is never asked. The next semantic pass loads that file into al-lsp through the bridge, and the next alc build passes it as `/analyzer:`, so the other user's code runs as the developer. Reproduced with a scratch test in `trust_tests.rs` (`r6_scratch_netpackages_link_outside_added_after_trust`): after the link, `decide` returns `Trusted` and `resolve("BusinessCentral.LinterCop")` returns the file under the linked directory, where it returned the NuGet copy before. A relative link such as `.netpackages -> ..` reaches the directories beside the clone in the same way, so a second repository the attacker controls works as a target on a machine with one user. When the name is one the record knows (repository settings or `~/.config/al-lsp/settings.json`), `project_analyzer_copies` hashes the outside file and the added link stales the record, but a file owned by another user can still be replaced between that hash and alc's load, since nothing checks it again.
- fix: judge the file by the search root discovery found it under. In `resolve`, treat a hit under any project search root (a relative probing path, `.netpackages`, `packages`) as a project copy whatever its canonical path, so `lists_project_copy` must list it. Simpler and stricter: in `find_best_below`, refuse a search root that is itself a link when the root is spelled inside the project (read it with `symlink_metadata`), as the walk already skips links below the root. Add `.netpackages`, `packages` and each relative probing path to `linked_package_folders`, so a link added or retargeted after the grant stales the record and `trust --show` prints where it resolves. Test: the scratch shape above is refused, and a link added after the grant makes the state `Stale`.
- status: open

### [SEC6-2] a path spelled inside the project that a link carries outside is recorded as its text, so the target and the link can change under the record
- where: crates/al-project/src/trust.rs:964 (`with_project_contents` returns the value as written when `stays_inside_project` is false, which it is for `./tools` when `tools` is a link to a directory outside the project), used for `al.codeAnalyzers` paths and `al.assemblyProbingPaths` (:1165-1233) and for `al.dotnetPath` and `lsp.al-lsp.binary.path` (:1538-1580)
- severity: low
- scenario: SEC5-1's fix hashes a linked path where it resolves and prints `resolves to` in `trust --show`, but only when the target is inside the project. A repository sets `"al.assemblyProbingPaths": ["./tools"]` and `"al.codeAnalyzers": ["./tools/TeamCop.dll"]` and ships `tools` as a link to a directory outside the clone, such as a shared analyzer checkout beside it or a directory another local user owns. `trust --show` prints `al.assemblyProbingPaths = ./tools` and `al.codeAnalyzers = ./tools/TeamCop.dll`, which read as files inside the project, with no hash and no sign of the link. After the grant, a change to the target's files, or a commit that points the link at a different outside directory, leaves the state `Trusted`, and the next build loads the new analyzer. Reproduced with a scratch test in `trust_tests.rs` (`r6_scratch_probing_path_link_retargeted_after_trust`): replacing `TeamCop.dll` in the target and then retargeting the link both leave `decide` at `Trusted`, and `resolve` returns the file under the new target. `"al.dotnetPath": "./tools/dotnet/dotnet"` through such a link records the same bare text, so the runtime it starts can change under the record too. Only a link present at grant time has this effect: a commit that turns a real `tools` directory into a link changes the recorded text and stales the record.
- fix: in `with_project_contents`, decide on the spelling: a path written inside the project is recorded with `resolves to <target>` whenever it resolves elsewhere, and the target's contents are hashed as they are for a target inside. Or refuse the grant for such a value with a message naming the link, as a link inside an analyzer tree is refused. Test: the scratch shape above prints the outside target in `trust --show`, and retargeting the link makes the state `Stale`.
- status: open

### [SEC6-3] comparing two lists or dictionaries that hold each other overflows the stack and aborts the daemon
- where: crates/al-runtime/src/interpreter/value.rs:376 and :378-384 (`Ord` for two different `List` or `Dict` handles compares snapshots of their contents element by element, with no record of the pairs already being compared), crates/al-runtime/src/interpreter/eval_expr.rs:1642 (`values_equal`, used by `=`, `<>` and `Assert.AreEqual`, falls back to that `Ord`), crates/al-runtime/src/interpreter/records.rs:2464 (the guard refuses only the receiver itself as an argument, so `A.Add(B); B.Add(A)` builds a cycle) and :3160 (`Dictionary.Set(1, D)` stores `D` in itself)
- severity: low
- scenario: a repository ships a test codeunit whose test does `A.Add(B); B.Add(A); C.Add(D); D.Add(C); if A = C then;` on four `List` variables, or `D1.Set(1, D1); D2.Set(1, D2); if D1 = D2 then;` on two dictionaries. The interpreter does not check element types, so the lists may be declared `List of [Integer]`. Comparing `A` with `C` compares `B` with `D`, then `A` with `C` again, without end. Local test runs need no trust. When the developer runs the project's tests with `al-explorer test-run` or `test-run-all`, or an agent runs them through the MCP tool `al_runtests` or the plugin skill `bc-test-locally`, the daemon runs the test on its interpreter thread (64 MiB stack), the stack overflows, and Rust aborts the whole daemon process. Every request in flight for that project fails, and the client sees `Connection closed by daemon (EOF)`. Reproduced twice: scratch tests `r6_scratch_compare_cycles` and `r6_scratch_dict_cycle` in `records_tests.rs` end the test binary with `thread '<unknown>' has overflowed its stack` (exit 134), and the release `al-explorer test-run 50391` on a copy of `al-test-harness/data/test_al_project` with such a test answered `{"error":"Connection closed by daemon (EOF)"}`, after which the project's `al-lsp daemon` process was gone. The next request starts a new daemon, so the damage is the lost work in flight and a test run that never reports. The call depth, expression depth and deadline caps do not apply, because the recursion is in Rust's `cmp` and not in AL.
- fix: compare reference types with a guard against cycles. Carry a set of the `(left, right)` handle pairs being compared through the list and dictionary arms of `cmp`, and treat a pair seen again as equal (the usual rule for comparing cyclic structures), or refuse to compare two lists or dictionaries in `values_equal` with an `Eval::Error`. Also refuse a `List` or `Dictionary` value that holds a handle leading back to itself when it is added, if the runtime should not build cycles at all. Test: both scratch shapes end with a result or an AL error, and the test binary survives.
- status: open

### [SEC6-4] `Contains`, `IndexOf`, `LastIndexOf` or `Remove` on a list in a cycle locks the list twice and hangs a daemon thread for good
- where: crates/al-runtime/src/interpreter/records.rs:2464-2473 (the list is locked for the whole method, and the guard against a double lock checks only whether an argument is the receiver itself), :2535-2537 (`contains` compares every element with the needle while the lock is held, and `indexof`, `lastindexof` and `remove` do the same), crates/al-runtime/src/interpreter/value.rs:31 and :376 (`Shared` is an `Arc<Mutex>`, and comparing two different lists takes `snapshot`, which locks each), crates/al-test/src/backends/interp.rs:398 (the interpreter thread is joined with no timeout)
- severity: low
- scenario: a test does `A.Add(B); B.Add(A); N.Add(E); if B.Contains(N) then;` on four `List` variables. `Contains` locks `B` and compares its element `A` with `N`. They are different lists, so `cmp` snapshots both and compares `B` with `E`, and the snapshot of `B` waits for the lock `B.Contains` already holds. A `std::sync::Mutex` locked twice on one thread does not return. The per-test deadline (30 s by default) is checked only between AL statements, so it never fires, and `run_codeunit_interp` waits on the thread's `join` forever. Reproduced with the release `al-explorer test-run 50392` on a copy of the harness project: `Daemon did not respond within 90s`, every daemon thread in `futex_wait` at 0% CPU, and the daemon's thread count up by three. The scratch test `r6_scratch_contains_cycle` in `records_tests.rs` hangs until `timeout` kills it. The daemon keeps answering other requests, so each such run costs one blocked test run, one or more threads and their stacks (the interpreter thread reserves 64 MiB), until the daemon exits. An agent that retries the test adds a thread each time.
- fix: take a snapshot of the receiver's items and release the lock before comparing (`let items = list.snapshot();`), and lock again only for the methods that change the list, or compare through the cycle safe comparison SEC6-3 asks for. Run the AL body under a watchdog that reports a test past its deadline as failed and returns, whether or not the thread ends. Test: the scratch shape returns within the deadline with a result or an error.
- status: open

### [SEC6-5] the local test runtime has no memory limit, so a test that doubles a text exhausts memory well inside its deadline
- where: crates/al-runtime/src/interpreter/eval_stmt.rs:224-230 and the other loop arms (the deadline and the cancel flag are checked once per loop iteration and nothing counts memory), crates/al-test/src/backends/interp.rs:156 (a 30 s deadline by default), crates/al-runtime/src/interpreter/records.rs:2459-2462 (`L.AddRange(L)` doubles a list in one call, and `T := T + T` doubles a text in one statement)
- severity: low
- scenario: a repository's test does `T := 'x'; for I := 1 to 40 do T := T + T;`. Each statement doubles the text, so the loop asks for 1 TiB in 40 statements, far faster than a 30 s deadline expires. Measured with the release `al-explorer test-run 50393` on a copy of the harness project, stopped at 29 doublings: the daemon built a 512 MiB text in 0.93 s and its resident size peaked at 1.2 GB. Each further doubling costs about twice the last, so a 16 GiB text is due within a few seconds more, and the machine swaps, or the allocation fails and Rust aborts the daemon, or the kernel's OOM killer picks a process, before the deadline check runs again. `L.AddRange(L)` in a loop does the same to a list. The run needs no trust and starts as SEC6-3 describes, from `al-explorer test-run`, `test-run-all`, `al_runtests` or the `bc-test-locally` skill. Not run past 512 MiB on this shared machine.
- fix: give the interpreter a budget. Cap the length of a Text, Code and TextBuilder value (Business Central's own limit for `Text` is about a billion characters, and a far lower cap such as 64 MiB still leaves real tests room) and the element count of a List or Dictionary, checked where values grow: concatenation, `PadStr`, `TextBuilder` methods, `Add` and `AddRange`. Report the cap as an AL error that fails the test. Test: the doubling loop fails with that error within a second.
- status: open
