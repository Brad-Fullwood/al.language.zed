### [R12-LIST-1] a List element and a search argument keep the argument's type, so a `List of [Code[20]]` misses what it holds
- where: crates/al-runtime/src/interpreter/records.rs:2461-2500 (`dispatch_list_method` pushes `Add`, `Insert`, `Set` and `AddRange` arguments as they come and compares `Contains`, `IndexOf`, `LastIndexOf` and `Remove` arguments with `==` on `Value`), against :3065 (`declared_key` converts every Dictionary key argument to the declared key type, the R10-DICT-1 fix), crates/al-runtime/src/interpreter/value.rs:66 (`Collection::member_type` carries the declared element type the list never uses for its elements)
- severity: medium
- scenario: R10-DICT-1 for lists. `L: List of [Code[20]]; L.Add('abc'); L.Contains('ABC')` is false locally and `L.Get(1)` is the Text `abc`, where BC converts the argument to `Code[20]` on `Add` (`ABC`) and `Contains('ABC')` is true. The shape a test hits first needs no conversion on `Add`: `L.Add(Item."No.")` from a Code field and `L.Contains('ITEM1')` with a text literal is false locally (`Value::Code("ITEM1")` and `Value::Text("ITEM1")` do not compare equal) and true on BC, so a test that collects numbers from records and asserts one is present is red locally and green on BC. Also `L.IndexOf('XYZ')` for a Code element gives 0. Confirmed with scratch `r12_scratch_collections` (`CodeListFromText` gives `missing`, `CodeListIndexOf` gives 0) and `r12_scratch_dispatch` (`CodeListFromField` gives `missing`, `CodeListContainsCodeVariable` with two Code variables gives `found`) in records_tests.rs. The List page on Learn says `T` "will change to" the declared type, so an argument is converted as any parameter is (AL variables, "Assignment and type conversion": Code and Text convert automatically). A `Dictionary of [Integer, Text]` keyed with a `Char` (`D.Add(S[1], 'x')`, `D.ContainsKey(97)`) is the same gap on the key side: `declared_key` falls to `coerce_into_slot`, which does not turn a Char into an Integer (`IntegerKeyFromChar` gives `missing`, BC converts Char to Integer).
- fix: convert every element argument of `Add`, `Insert`, `Set`, `AddRange` and every search argument of `Contains`, `IndexOf`, `LastIndexOf`, `Remove` to `member_type()` before it is stored or compared, with the `declared_key` rules (Code upper-cased and trimmed, capacity checked), and add the Char to Integer case to `declared_key`. Pin the Code field shape and the Char key.
- status: open

### [R12-LIST-2] `Keys()` and `Values()` return lists with no declared type, so a typed variable that takes one loses its `AddRange` overload and Code conversion
- where: crates/al-runtime/src/interpreter/records.rs:3222-3237 (`keys` and `values` build `Value::list(...)`, "with no declared element type"), :2620-2640 (`adds_elements` takes `AddRange(List of [T])` for a list whose `member_type()` is `None`), crates/al-runtime/src/interpreter/value.rs:68-70 (a `Dict` `Collection` keeps only its key type, so `Values()` has no type to give)
- severity: low
- scenario: `D: Dictionary of [Integer, List of [Integer]]; Vals: List of [List of [Integer]]; Inner: List of [Integer]` with `Inner.AddRange(1, 2, 3); D.Add(1, Inner); Vals := D.Values(); Vals.AddRange(Inner); exit(Vals.Count())` returns 4 locally: the value `Vals` now refers to has no element type, so `adds_elements` splices Inner's three elements. BC picks `AddRange(T)` for a list whose `T` is a List and adds `Inner` as one element, so the count is 2 (the R10-LIST-1 rule, applied to a list that came from `Values()`). The same loss of type makes `K := D.Keys(); K.Add('b'); K.Contains('B')` false for a `Dictionary of [Code[20], Integer]` (with R12-LIST-1 fixed it would still be false, since the value carries no type to convert to). Confirmed with scratch `r12_scratch_collections` (`ValuesThenAddRange` gives 4, `KeysThenAdd` gives `missing`).
- fix: keep both type arguments on a Dictionary `Collection` and give `Keys()` the key type and `Values()` the value type. Alternatively, when a List value with no type is assigned to a variable declared with one, stamp the variable's type on the value. Pin the `Values()` list of lists shape.
- status: open

### [R12-RT-1] overloads that differ only by record subtype run the first declaration
- where: crates/al-runtime/src/interpreter/dispatch/workspace_procedure.rs (`choose_overload`, the R10-RT-2 fix: a candidate is taken when `check_param_type` accepts every argument, then the most exact base type names win, then declaration order), crates/al-runtime/src/interpreter/dispatch/frames.rs:388-421 (`check_param_type` matches on the base keyword only and its `_ => {}` arm accepts any value for a `Record` parameter), crates/al-runtime/src/interpreter/value.rs:586 (`type_name` of a record is `Record`, so both overloads count as exact)
- severity: low
- scenario: a codeunit with `procedure Describe(C: Record "R12 Cust"): Text` returning `cust` and `procedure Describe(V: Record "R12 Vend"): Text` returning `vend`. `Describe(C) + '|' + Describe(V)` gives `cust|cust` locally and `cust|vend` on BC, since alc chooses the overload by the argument's table. Nothing reports the choice, so a test of a helper overloaded per table (`Apply(var SalesHeader: Record "Sales Header")` beside `Apply(var PurchHeader: Record "Purchase Header")`) runs the wrong body. Confirmed with scratch `r12_scratch_dispatch` (`ByRecordOverload`) in records_tests.rs. Overloads by scalar type, by argument count and by position (`Pair(1, 'x')` and `Pair('x', 1)`) hold in the same scratch, as does a Code variable choosing `Code[20]` over `Text`.
- fix: in `choose_overload`, when a parameter is `Record <Subtype>` compare the subtype with the argument's `table_name` (unquoted, case-insensitive) and refuse the candidate on a mismatch, and give `Codeunit <Subtype>` the same treatment. Pin the two-table shape.
- status: open

### [R12-RT-2] the `var` write back to an array element reads the index after the call, so a callee that moves the index writes the wrong element
- where: crates/al-runtime/src/interpreter/eval_stmt.rs:993-995 (`write_var_argument`, the R11-RT-2 fix, calls `indexing::write_element` with the argument's suffix node, which evaluates the index expression at write time, after the callee returned)
- severity: low
- scenario: a global `I`, a local `Amounts: array[3] of Integer`, `I := 1; Bump(Amounts[I])` where `Bump(var N: Integer)` sets `I := 2` and then `N += 1`. BC binds the reference to `Amounts[1]` before the call and returns `Amounts[1] = 1, Amounts[2] = 0`. Locally the write goes to `Amounts[2]` (`0/1`), since the index is read again after `Bump` changed `I`. An index with a side effect is evaluated twice: `Bump(Amounts[NextIndex()])`, where `NextIndex` increments a counter and returns it, bumps `Amounts[2]` and leaves the counter at 2 where BC bumps `Amounts[1]` and leaves it at 1 (`IndexEvaluatedTwice`). Confirmed with scratch `r12_scratch_dispatch` (`IndexReadAfterCallee` gives `0/1`) in records_tests.rs. The `var` pass-through (`Outer(var A)` calling `Inner(A)`) and the two dimension refusal hold in the same scratch.
- fix: evaluate the index of an indexed `var` argument once, before the call, when the argument values are collected, and pass the resolved element position to the write back. Pin the moved index shape.
- status: open

### [R12-KW-1] a record method the runtime lacks, written without parentheses, still routes locally and fails as a missing field
- where: crates/al-test/src/router/ast.rs:715-747 (the router classifies a record method only from a call suffix, so `R.LockTable;` is a member read and gets no `unsupported Record.LockTable` reason), crates/al-runtime/src/interpreter/eval_expr.rs (the R10-KW-1 branch runs a member without parentheses only when `supports_record_method` or a table procedure accepts it)
- severity: low
- scenario: two test codeunits over a workspace table, one with `R.LockTable();` and one with `R.LockTable;`. The router sends the first to live BC (`calls unsupported Record.LockTable (requires BC semantics)`) and keeps the second local (`InterpRecord`, `uses workspace record table`), where it fails at run time as a field read. The R10-KW-1 status line records this gap. It is listed here because the routing answer differs by the parentheses alone, and CodeCop AA0008 is a warning, so the form is in real test code. Confirmed with scratch `r12_scratch_record_method_without_parentheses_routing` in router/tests.rs.
- fix: in the router's member classification, treat a member access on a record variable with no call suffix and no field of that name in the table as a call, and apply the `supports_record_method` rule to it.
- status: open

### [R12-GR-1] the grammar does not accept a quoted identifier as the `for` loop variable
- where: the grammar at 142aba6 (the submodule `extension.toml` names), read through `al_syntax::parser::language()`: `for "My Index" := 1 to 3 do` parses as an `ERROR` node at `for` and another at `1 to 3 do`, while `foreach "My Item" in L do` and `"My Index" := 1` parse
- severity: low
- scenario: a procedure with `var "My Index": Integer;` and `for "My Index" := 1 to 3 do T += Format("My Index");`. alc compiles it (any variable can be the loop variable). Locally the runtime answers `unsupported expression kind: ERROR`, and every object in the same file is refused as containing syntax errors, so a table declared in that file fails all its tests with `record table ... contains syntax errors`. R10-RT-1 made quoted names readable in expressions and case labels, and the loop header is the shape left. Confirmed with scratch `r12_scratch_quoted_loop` in records_tests.rs, which prints the two ERROR nodes and runs the plain-name loop (`123`) and the quoted `foreach` (3).
- fix: in the grammar's `for_statement`, accept the same identifier rule the `foreach` and assignment rules take for the loop variable. Add the shape to the grammar corpus. Until then, the runtime could report the ERROR node's position rather than `unsupported expression kind`.
- status: open

### [R12-MUT-1] seven formatter tests pin the indentation of text that is not AL, so they pin the state machine rather than a formatting contract
- where: crates/al-syntax/src/formatting/indent.rs, the tests `end_without_semicolon_defers_its_slot_until_the_next_line_is_not_else` (an `end` with no `;` followed by a statement), `a_begin_ending_line_that_is_not_bare_begin_drains_a_pending_single_statement` (`MyLabel: begin`, and its comment says "the formatter's indentation state machine does not care whether the label is valid AL"), `a_trailing_colon_line_outside_any_case_is_not_a_label` (`MyGlobalLabel:`), `a_case_label_body_ending_in_a_bare_end_closes_the_case_exactly_once` (`AfterLabel:` after the case), `an_empty_case_closed_by_end_semicolon_fused_with_more_code_decrements_case_depth` (`end; Y := 1;` then `Z:`), `an_if_with_no_then_is_not_a_single_statement_opener` (`if x > 0` with no `then`) and `a_semicolon_terminated_close_applies_its_carried_slot_immediately` (`end;` before `else`, which alc refuses)
- severity: low
- scenario: AL has no labels, an `end` before another statement needs `;`, `if` needs `then`, and `end; else` is a compile error, so none of the seven inputs is code the formatter is asked to format on purpose. Each test asserts one exact output, chosen to be whatever the current state machine produces (for example `Message('a')` at the level of an `if` that has no `then`, and `MyLabel: begin` at the level of the `if` above it). `mutants.md` records them as the tests that kill mutants in `indent.rs`, which they do, and a later change that handles incomplete code differently, or that keeps the formatter from touching text with syntax errors, must rewrite all seven with no reader able to say which output was right. The other tests the round added (the `var` section ends, `object_level_var_section_closed_directly_by_the_closing_brace`, the `passes.rs` and `text.rs` unit tests, the `range.rs` edit shapes, the `composition.rs` warning tests and the `cobertura.rs` rate tests) assert values a reader can derive from the input, and are not in this finding.
- fix: for each of the seven, either replace the input with valid AL that reaches the same branch (a nested `if ... then begin ... end` without `;` followed by `else` is valid, a `case` with an empty body is valid) or state in the test's comment that the output is the formatter's stability guarantee for text mid-edit, with the property that matters (no line moves twice, the file is unchanged on a second pass) asserted instead of the exact indentation.
- status: open
