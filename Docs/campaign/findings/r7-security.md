Threat model: a developer clones a hostile repository, opens it in the editor or runs `al-explorer` on it before trusting it, and trusts it later while the repository keeps changing. A second attacker is a local process of another user on a shared machine. A third is whoever can put bytes in front of the plugin's release download. The assets are the user's credentials, the trust digest, the daemon, and what the developer's terminal shows.

Tools: reading the source, scratch tests run one crate at a time with `cargo test`, and shell probes of the plugin scripts. Scratch tests are named `sec7_scratch_...` and stay uncommitted in the review worktree.

### [SEC7-2] the trust record hashes every byte of every file in a linked tree, so a large file the link reaches keeps every trust decision busy, before trust and from the repository's files alone
- where: crates/al-project/src/trust.rs:1096 (`file_sha256` copies the whole file into the hasher), :1170 (`collect_files` counts entries against `MAX_HASHED_ENTRIES` and nothing counts bytes), :1132 and :1072 (`tree_sha256` and `file_and_neighbours_sha256` hash the found file and every regular file in its directory's tree), :1020 (`with_project_contents` hashes a path spelled inside the project wherever a link carries it, the SEC6-2 fix), :579 (`project_analyzer_copies` hashes the same file again in the same read, so `read_repository` at :480 hashes each tree twice per decision), crates/al-project/src/analyzers.rs:200 (`resolve` decides trust on an untrusted project too), crates/al-lsp/src/server/lsp/mod.rs:821-823 (`SessionGate::read` decides at `initialize`), crates/al-lsp/src/server/daemon/mod.rs:198 (the daemon decides at start), crates/al-lsp/src/server/daemon/containment.rs:338 (`decide` again on every request with a path parameter while a package folder resolves outside the project)
- severity: low
- scenario: the SEC6-1 and SEC6-2 fixes hash a linked outside tree, which STATE.md queued as "hashed up to the 50,000 entry cap with no byte limit". Two shapes. With the repository alone: a clone ships `tools` as a link to `/proc/self` and `"al.codeAnalyzers": ["./tools/pagemap"]` in `.vscode/settings.json`. `pagemap` is a regular file the kernel serves for the reading process at 256 GiB on a 47 bit address space (`dd` reads it at 9.9 GB/s here). `names_a_project_file` is true for the spelling, `canonicalize` gives `/proc/<pid>/pagemap`, `metadata.is_file()` is true, and `file_sha256` reads it to the end before the directory walk meets the first link and gives up. Reproduced with the scratch test `sec7_scratch_pagemap_through_a_link` in `trust_tests.rs`: `decide` on the untrusted project had not returned after 45 s. With a second user of the machine, or a large file the link happens to reach: `tools -> /tmp/bc-tools` and `"al.codeAnalyzers": ["./tools/x/TeamCop.dll"]`, where the other user puts a sparse 2 GiB `big.bin` beside the analyzer. Reproduced with `sec7_scratch_linked_tree_hash_reads_every_byte`: `decide` took 87.9 s in the test build and `CustomAnalyzerSearch::resolve` on the untrusted project 126.5 s, both with the state `Untrusted`, since `read_repository` hashes the tree in `with_project_contents` and again in `project_analyzer_copies`. The test build's SHA-256 is far slower than the machine's: `sha256sum` reads the same 2 GiB sparse file in 1.36 s, so a release build pays about 0.7 s per GiB per hash, some six minutes for the two hashes of `pagemap`, and the file's size is the attacker's choice. The developer pays it without trusting anything: at the language server's `initialize`, at the daemon's start, in `al-explorer trust --show`, on each semantic pass that resolves an analyzer, and on each daemon request with a path parameter once `.alpackages` is a link. Nothing in the hash is skipped for a FIFO or a device node (`is_file` is false for both), and a file swapped for a FIFO between `read_dir` and `File::open` blocks the open, which the other user can do in a loop [UNVERIFIED: a scratch test that races the swap would show it].
- fix: cap the bytes a tree hash reads, beside the entry cap: stop at a budget such as 256 MiB per tree and record `not hashed, <dir> holds more than N MiB` the way `TooManyEntries` is recorded, so a grant is refused with the reason and a record over it goes stale. Refuse a file whose `metadata.len()` is over the budget before opening it, and count bytes as they are read so a file that reports no length (`/proc`) stops at the budget too. Hash each tree once per `read_repository`: `with_project_contents` and `project_analyzer_copies` compute the same hash for the same file. Open files with `O_NONBLOCK` on Unix and refuse one that is not a regular file after the open, so a swap to a FIFO fails instead of blocking. Test: the two scratch shapes return within a second with the state `Untrusted` and the reason in the record.
- status: open
