Threat model: a developer clones a hostile repository, opens it in the editor or runs `al-explorer` on it before trusting it, and trusts it later while the repository keeps changing. A second attacker is a local process of another user on a shared machine. A third is whoever can put bytes in front of the plugin's release download. The assets are the user's credentials, the trust digest, the daemon, and what the developer's terminal shows.

## Findings

### [SEC8-1] the byte budget and the entry cap bound one hash, and nothing bounds how many hashes one decision runs
- where: crates/al-project/src/trust.rs:1240 (`MAX_HASHED_BYTES` is the most one hash reads), :1232 (`MAX_HASHED_ENTRIES` is the most one walk inspects, and the `Runtime` shape walks three times), :1323-1358 (`Hashes` memoises by resolved path and shape, so N distinct paths are N reads), :1544 and :1602 (every `al.codeAnalyzers` entry and every `al.assemblyProbingPaths` entry the repository writes is hashed, with its directory), crates/al-project/src/config.rs:723 (`MAX_EDITOR_SETTINGS_BYTES`, 1 MiB, is the only bound on how many entries a settings file holds), against the decision sites SEC7-2 listed: crates/al-project/src/analyzers.rs:227 (`resolve` decides before trust), crates/al-lsp/src/server/daemon/containment.rs:339 (`decide` again per request with a path parameter)
- severity: low
- scenario: a repository's `.vscode/settings.json` lists `al.assemblyProbingPaths: ["./t0", "./t1", ... "./t999"]` and ships a 200 MiB file of zeros in each directory. The pack compresses each to a few kilobytes, the checkout writes 200 GiB, and each trust decision reads it again: `decide` before trust, `resolve` per analyzer lookup, and the daemon's per request check. `sec8_scratch_n_trees_each_under_the_budget_read_n_budgets_per_decision` sets the budget to 1 MiB, names 16 directories with a file just under it, and `HASHED_BYTES_READ` shows 15 budgets read by one decision with no refusal. The same holds for entries that name directories outside the project: each is one walk of up to 50,000 entries before its listed length refuses it, so a thousand `/usr/share/<x>` entries cost a thousand walks per decision. [UNVERIFIED: the time a decision takes at the real budget with a clone of that shape, which needs the 200 GiB checkout]
- fix: give `Hashes` a per decision total of bytes read and entries walked beside the per hash limits, and return `Unhashable::TooManyBytes` (or a new reason) for every hash after the total passes `MAX_HASHED_BYTES`, so the decision refuses the grant with one reason and stops reading. Test: the scratch shape with the budget at 1 MiB and 16 directories reads at most one budget and records a refusal.
- status: open

### [SEC8-2] an `al.dotnetPath` the repository writes outside the project is recorded as its text, with no mark of whether the file exists, and a trusted project runs whatever appears there later
- where: crates/al-project/src/trust.rs:1136 (`with_path_contents` returns the value as written for `Outside::AsWritten` before the `canonicalize` that adds `(not present)` and before any hash), :1964 (`executable_path_privileges` passes `al.dotnetPath` and `lsp.al-lsp.binary.path` as `AsWritten`, under the comment at :1108 that they "name a program on the user's machine"), :2053 (`enforce_dotnet_path` keeps `AL_DOTNET_PATH` on a trusted project with no look at the file), :2089-2106 (`enforce_dotnet_path_before_spawn` returns before deciding for a host outside the project), against :1530 (`privileged_changes` records only what the repository's files add over the user's, so every recorded `al.dotnetPath` is the repository's choice) and src/lib.rs:649 (the Zed extension turns the merged `dotnetPath` into `AL_DOTNET_PATH`, so `.zed/settings.json` in the clone reaches the spawn)
- severity: low
- scenario: a clone's `.zed/settings.json` sets `lsp.al-lsp.settings.dotnetPath` to `/tmp/dotnet-9/dotnet` (or any path in a directory another local user can write). `al-explorer trust` prints `al.dotnetPath = /tmp/dotnet-9/dotnet` and nothing says the file is absent. The developer grants. The second user then creates `/tmp/dotnet-9/dotnet`, and `decide` still answers `Trusted`, `enforce_dotnet_path` returns `None` and keeps `AL_DOTNET_PATH`, and the next build or analyzer load runs that program as the developer. The scratch test pins each step with a temp directory in place of `/tmp/dotnet-9`. The same path inside the project would have been recorded with its hash and the runtime beside it, and a probing path at the same outside place would have been recorded `(not present)` and gone Stale when the file appeared (SEC7-4).
- fix: record an outside `al.dotnetPath` as `Outside::Hashed` with `Beside::Nothing`, so an absent host records `(not present)` and a present one records the muxer's hash, and a file that appears or changes after the grant stales the record without hashing a system runtime past the byte budget. Have `enforce_dotnet_path_before_spawn` decide for an outside host too, since the decision then costs one file hash. Test: the scratch shape records `(not present)`, and the file that appears after the grant makes `decide` answer `Stale` and `enforce_dotnet_path` drop the variable.
- status: open

### [SEC8-3] a link the repository ships at `app.json` or a settings file to a device or FIFO stalls or aborts every reader before trust, because the length check follows the link and the read has no bound of its own
- where: crates/al-project/src/project.rs:412-417 (`load_app_manifest` takes the length from `std::fs::metadata`, which follows a link), :428 (`read_to_string` then reads to end of file), :406 (`MAX_APP_JSON_BYTES` is the only bound), crates/al-project/src/config.rs:863-870 (`read_editor_settings_file` does the same for `.vscode/settings.json` and `.zed/settings.json`) and :383-390 (the other settings reader), crates/al-project/src/trust.rs:494 (`inspect` and `decide` read both settings files through it, before the project is trusted), crates/al-lsp/src/server/workspace/mod.rs:134 (`find_project` at `initialize` reads `app.json`), crates/al-workspace/src/lib.rs:1755 and crates/al-lsp/src/server/daemon/mod.rs:894 (the daemon reads it again before each request), against crates/al-project/src/project.rs:470-475 (`load_launch_configs` reads with `take(MAX_APP_JSON_BYTES + 1)`, so a device there stops at the cap) and crates/al-project/src/trust.rs:1526 (`open_regular_file`, the SEC7-2 open that refuses a file that is not regular once open)
- severity: low
- scenario: a clone holds `app.json -> /dev/zero` (git checks a symbolic link out on Linux and macOS). `metadata` reports length 0, under the cap, and `read_to_string` grows its buffer until allocation fails and the process aborts: the language server at `initialize`, the daemon at start, and `al-explorer` on any command, before anyone is asked to trust the project. A link to a FIFO blocks the reader instead: `sec8_scratch_a_link_at_app_json_to_a_fifo_blocks_the_manifest_load` links `app.json` to a FIFO in the same directory and `load_app_manifest` has not returned after 3 s. The same link at `.zed/settings.json` reaches the trust decision itself through `read_editor_settings_file`. [UNVERIFIED: the abort on `/dev/zero`, which needs a run under an address space limit, and `/dev/stdin` on the language server, which would read the editor's own transport]
- fix: read the four project files the way `open_regular_file` and `load_launch_configs` do: open, refuse anything that is not a regular file once open (`symlink_metadata` before it refuses the link itself, as the trust hash does), and read with `take(cap + 1)`, so a device or FIFO is an error the reader names. One helper in `al_project` for `app.json`, the two settings files and the launch files. Test: the scratch shape returns an error within the timeout, and a link to a regular file inside the project still loads.
- status: open

### [SEC8-4] the held byte budget counts collections, arrays and text builders, so a test holds many capped texts in scalar variables and recursion frames instead
- where: crates/al-runtime/src/interpreter/value.rs:693 (`MAX_HELD_BYTES`, 256 MiB), :709 (`hold_bytes`, the check), :748 (`owned_bytes` counts text in arrays and in collection elements), crates/al-runtime/src/interpreter/records/collection_methods.rs:95, :919, :934, crates/al-runtime/src/interpreter/json.rs:212 and crates/al-runtime/src/interpreter/indexing.rs:193 (the charged sites: List, Dictionary, JSON and array element writes), against value.rs:896 (`coerce_into_slot`, the assignment into a variable, which charges nothing), :668 (`MAX_TEXT_BYTES`, 64 MiB for one value) and crates/al-runtime/src/interpreter/dispatch/mod.rs:85 (`MAX_RECURSION_DEPTH`, 512 frames)
- severity: low
- scenario: `sec8_scratch_scalar_texts_and_frames_are_outside_the_held_byte_budget` runs a codeunit whose `InLocals` fills nine `Text` locals with 32 MB each (274 MiB, past the budget) and whose `InFrames` recurses ten deep with a 32 MB local per frame, and both return normally. The same 274 MiB in a `List of [Text]` fails with "List.Add would make ... limit of 256 MiB for one test" (`copies_of_a_large_text_stop_at_the_test_budget`). At the caps a test reaches 512 frames of 64 MiB, 32 GiB, inside the deadline, or a codeunit with a few hundred global `Text` variables holds the same with no recursion.
- fix: charge a text assignment into a variable slot as the array element write is charged (`hold_bytes` in `coerce_into_slot` with the release of what the slot held), and release a frame's locals when the frame returns, so scalar and collection text count against the one budget. Test: the scratch shape fails with the budget message on the fifth local and on the ninth frame.
- status: open
